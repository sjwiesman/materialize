# BM25 full text search index (POC)

## Summary

A proof of concept that adds BM25-ranked full text search to Materialize,
backed by the dd-bm25 approach: a custom differential dataflow batch container
that embeds an inverted index (postings lists plus an FST) built at batch seal
time. Users create a search index with `CREATE INDEX ... WITH (BM25)` and query
it with a ParadeDB-style `@@@` operator plus an `mz_score()` function for
ranking. Only ad-hoc SELECTs (peeks) are supported. Dataflows cannot be built
on top of the search arrangement.

This is a POC. It may panic outside the happy path, but the happy path should
generally work, including updates and deletes to indexed rows.

## SQL surface

```sql
CREATE INDEX items_search ON items (description) WITH (BM25);

SELECT id, description, mz_score() AS score
FROM items
WHERE description @@@ 'running shoes'
ORDER BY score DESC
LIMIT 10;
```

* `BM25` is a new `IndexOptionName` variant, following the `RetainHistory`
  pattern. Plan-time validation requires exactly one key expression, and it
  must be a column reference of type `text`. Anything else is a plan error.
* `@@@` resolves to a new `BinaryFunc` with signature `(text, text) -> bool`.
  Its `eval` panics. The function only exists to be pattern-matched out of the
  plan by the peek rewrite. If it survives to evaluation, for example because
  there is no BM25 index or the plan shape is not recognized, the query fails.
  That is the accepted POC failure mode.
* `mz_score()` is a new `UnmaterializableFunc` returning `double precision`.
  The rewrite replaces it with a column reference. It errors if it survives
  planning.
* The search string is bag-of-words: tokenized with dd-bm25's
  `DefaultTokenizer` (alphanumeric split, lowercase), terms combined with OR
  semantics, exact term match only (edit distance 0).
* BM25 parameters are fixed at k1 = 1.2, b = 0.75. The tokenizer is not
  configurable.
* Rows whose text column is NULL are not indexed and never match.

## Architecture

Two integration hot spots: building a BM25-spined arrangement on compute, and
routing an ad-hoc SELECT to it with the query string attached.

### New crate: `src/bm25` (mz-bm25)

A port of dd-bm25's `tokenize`, `index`, `search`, `query`, `container`, and
`operators` modules onto the workspace's differential-dataflow 0.25 and timely
0.31. The upstream repo targets dd 0.18, so trait signatures need updating,
but the `Layout`, `BatchContainer`, and `Builder` extension points still
exist.

The layout is instantiated concretely for Materialize: key = `String`
(the indexed text), value = `Row` (the full source row), time =
`mz_repr::Timestamp`, diff = `mz_repr::Diff`. Each sealed batch carries a
`Bm25Index` over its keys. The upstream streaming `bm25_search` operator,
fuzzy matching, and boolean query builder are dropped. Peeks search batches
directly.

New workspace dependency: `fst` (Unlicense OR MIT), added to root
`Cargo.toml` workspace dependencies, `deny.toml`, and `about.toml` as needed.

### Catalog and planning

* `plan_create_index` carries a `bm25: bool` through `Plan::CreateIndex` into
  the in-memory catalog `Index` struct. The option round-trips through AST
  display, so the durable catalog, which stores CREATE SQL text and re-plans
  it, needs no schema change.
* BM25 indexes are excluded from the optimizer's index oracle and compute
  instance snapshot. Joins, point lookups, and plain `SELECT * FROM items`
  never route to the BM25 arrangement. Its shape (String keys, embedded
  index) is unusable for those purposes.
* `IndexDesc`, or the index import metadata alongside it, gains the flag so
  compute's render path knows to build the BM25 arrangement instead of the
  RowRow one.

### Peek routing in the adapter

`create_fast_path_plan` (src/adapter/src/coord/peek.rs) gains a new match arm
ahead of the existing `PeekExisting` arm. It fires when the plan is an MFP
over `Get(t)`, the MFP's filter predicates contain
`bm25_match(#c, <string literal>)`, and the catalog has a BM25 index on `t`
keyed by column `c`. The peek optimizer passes the set of BM25 indexes into
`create_fast_path_plan`, which otherwise has no catalog access.

On match, the rewrite:

1. Strips the `bm25_match` predicate from the MFP.
2. Replaces `mz_score()` occurrences with a reference to a score column
   appended after `t`'s columns, and builds the remaining `SafeMfpPlan` over
   `(row ++ score)`.
3. Emits a new `FastPathPlan::PeekBm25(coll_id, idx_id, query_string, mfp)`.
4. Inserts the BM25 index into the dataflow's `index_imports`, so read holds,
   timestamp selection, and EXPLAIN's "Used Indexes" flow through existing
   machinery.

The plan lowers to a new `PeekTarget::Bm25Index { id }` variant plus the
query string on the `Peek` command. `PeekTarget` is plain serde, no proto
changes needed. `ORDER BY` and `LIMIT` ride the existing `RowSetFinishing`
untouched, since `mz_score()` is a plain output column by that point.

### Compute: rendering and storage

* `export_index` branches on the BM25 flag. Instead of the RowRow
  `MzArrange`, it keys the collection by the text column extracted as a
  `String`, dropping NULLs, with the full `Row` as the value, and arranges
  with the ported `Bm25Batcher`, `Bm25Builder`, and `Bm25Spine`. Every sealed
  batch builds its inverted index in the builder's `done`/`seal`. Errors
  still arrange into the standard errs trace.
* `TraceManager` gains a parallel map, `bm25_traces: BTreeMap<GlobalId,
  Bm25TraceBundle>`, holding the BM25 oks trace and the standard errs trace.
  Compaction (`allow_compaction`), maintenance, and frontier reporting loop
  over both maps, so the controller's bookkeeping is unchanged.

### Compute: peek execution

A new branch in peek handling (src/compute/src/compute_state.rs) matches
`PeekTarget::Bm25Index`, looks up the trace in `bm25_traces`, and:

1. Visits each batch via `map_batches`.
2. Runs the bag-of-words query against the batch's embedded `Bm25Index`,
   producing doc id to score.
3. Maps doc ids back to `(key, row, time, diff)` through the batch cursor.
4. Accumulates per `(key, row)`: diffs summed for times less than or equal to
   the peek timestamp, score taken from the most recent batch that scored the
   doc.
5. Emits `(row ++ score)` for entries with positive accumulated count, then
   applies the `SafeMfpPlan` and hands rows to the existing finishing and
   response path.

Each worker answers over its own shard, as with regular index peeks.

## Known POC approximations

Documented, deliberately not fixed:

* IDF statistics are per batch and per worker. Scores are only globally
  consistent once compaction has merged history into a single batch per
  worker. Rows present in a batch as retractions still count toward that
  batch's corpus statistics.
* Any `@@@` query the rewrite does not match (joins, a non-literal query
  string, no BM25 index on the filtered column) errors or panics.
* No fuzzy matching, no boolean query syntax, no configurable tokenizer or
  BM25 parameters.
* Peeks only. The BM25 index cannot serve as an input arrangement for other
  dataflows, and the optimizer never selects it for anything but the search
  rewrite.
