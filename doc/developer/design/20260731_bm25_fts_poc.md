# BM25 full text search index (POC)

## Summary

A proof of concept that adds BM25-ranked full text search to Materialize,
backed by the dd-bm25 approach: a custom differential dataflow batch container
that embeds an inverted index (postings lists over exact terms) built at batch
seal time. Users create a search index with `CREATE INDEX ... WITH (BM25)` and
query it with a ParadeDB-style `@@@` operator plus an `mz_score()` function for
ranking. Searches are answered by ad-hoc SELECTs (peeks) only. No dataflow can
be built on top of the search arrangement.

This is a POC. It may panic outside the happy path, but the happy path should
generally work, including updates and deletes to indexed rows.

This document describes the feature as built.

## SQL surface

```sql
CREATE INDEX items_search ON items (description) WITH (BM25);

SELECT id, description, mz_score() AS score
FROM items
WHERE description @@@ 'running shoes'
ORDER BY score DESC
LIMIT 10;
```

* The feature is behind the `enable_bm25_index` feature flag, off by default.
  Planning a `WITH (BM25)` index without it is an error. Only index creation is
  gated. An index that already exists keeps serving searches whatever the flag
  says.
* `BM25` is a new `IndexOptionName` variant, following the `RetainHistory`
  pattern. It is a boolean option defaulting to false, so `WITH (BM25 = false)`
  names a plain index. Plan-time validation requires exactly one key
  expression, and it must be a column reference of type `text`. Anything else
  is a plan error. `ALTER INDEX` rejects setting or resetting the option, so
  the flag is fixed at creation.
* `@@@` resolves to a new `BinaryFunc` with signature `(text, text) -> bool`.
  The function exists to be pattern-matched out of the plan by the peek
  rewrite. A call the rewrite cannot consume, because there is no BM25 index on
  the filtered column or the plan shape is not recognized, is rejected at
  planning with SQLSTATE 0A000 instead of being left to reach `eval`. That
  guard lives in `create_fast_path_plan`, so it covers peeks only. A call that
  reaches `eval` anywhere else returns `EvalError::Unsupported`. See known
  limitations.
* `mz_score()` is a new `UnmaterializableFunc` returning `double precision`.
  The rewrite replaces it with a reference to the score column the BM25 peek
  appends. One-shot expression preparation leaves `mz_score()` in the plan
  rather than evaluating it, so the rewrite gets to see it. A call the rewrite
  does not consume is rejected at planning with SQLSTATE 0A000.
* The search string is bag-of-words: tokenized by `mz_bm25::tokenize`
  (ASCII-alphanumeric split, lowercased, tokens over 40 bytes dropped), terms
  combined with OR semantics, exact term match only. Documents and queries run
  through the same function, so text outside ASCII-alphanumeric ranges, CJK for
  example, is not searchable.
* BM25 parameters are fixed at k1 = 1.2, b = 0.75. The tokenizer is not
  configurable.
* Rows whose text column is NULL are not indexed and never match.

## Architecture

Two integration hot spots: building a BM25-spined arrangement on compute, and
routing an ad-hoc SELECT to it with the query string attached.

### New crate: `src/bm25` (mz-bm25)

A port of dd-bm25's tokenizer, index, query evaluation, and container onto the
workspace's differential-dataflow and timely versions, landing as the modules
`tokenize`, `index`, `query`, and `spine`. The upstream repo targets an older
differential, so trait signatures need updating, but the `Layout`,
`BatchContainer`, and `Builder` extension points still exist.

The layout is instantiated concretely for Materialize: key = `String`
(the indexed text), value = `Row` (the full source row), time =
`mz_repr::Timestamp`, diff = `mz_repr::Diff`. A batch sealed by the builder
carries a `Bm25Index` over its keys. The upstream streaming `bm25_search`
operator, fuzzy matching, and boolean query builder are dropped. Peeks search
batches directly.

Dropping fuzzy matching drops the FST with it. Terms match exactly, so the
embedded index is a term to postings map plus the document lengths and corpus
averages scoring needs, and nothing more. The crate takes no third-party
dependency beyond differential dataflow and timely.

Merging batches does not merge their indexes. The `BatchContainer` merge path
copies keys through `push_ref`/`push_own` and offers no seal hook to build one
in, so a merged batch carries a default index whose `is_built()` is false. The
peek path checks that flag per batch and rebuilds the index from the batch's
texts when it is unset.

### Catalog and planning

* `plan_create_index` carries a `bm25: bool` through `Plan::CreateIndex` into
  the in-memory catalog `Index` struct. The option round-trips through AST
  display, so the durable catalog, which stores CREATE SQL text and re-plans
  it, needs no schema change.
* A BM25 index serves everything a plain index on the same key serves, through
  its standard arrangement, plus `@@@` peeks through its search arrangement.
  That contract holds on tables, views, and materialized views alike. The
  optimizer therefore treats a BM25 index as an ordinary index. The index
  oracle offers it for join planning, `import_into_dataflow` imports it, and
  `sufficient_collections` names it. Joins, point lookups, and plain
  `SELECT * FROM items` read the standard arrangement. Only the peek path
  reaches the search arrangement, whose shape (String keys, embedded index) is
  unusable for anything else.
* All three read `DataflowBuilder::indexes_on`, so import and timestamp
  selection always agree on whether an object is served by an index or read
  from its inputs. The `IndexAlreadyExists` notice is the one place that still
  narrows by the `bm25` flag, so a search index and a plain index on the same
  key are not reported as duplicates of each other.
* `IndexDesc` gains the flag so compute's render path knows to build the BM25
  arrangement alongside the RowRow one.

### Peek routing in the adapter

`create_fast_path_plan` (src/adapter/src/coord/peek.rs) gets first refusal for
the BM25 rewrite, ahead of the existing `PeekExisting` arm. The rewrite fires
when the plan is an MFP over `Get(t)`, the MFP's filter predicates contain
`bm25_match(#c, <string literal>)`, and the catalog has a BM25 index on `t`
keyed by column `c` that the compute instance tracks. `create_fast_path_plan`
takes an `OptimizerCatalog` and a `ComputeInstanceSnapshot` so that it can look
that index up. `t` can be a plain view as readily as a table or a materialized
view. Importing the view's BM25 index keeps `Get(view)` alive through dataflow
import instead of inlining the view's definition, which is what leaves the
rewrite something to match on.

On match, the rewrite:

1. Strips the `bm25_match` predicate from the MFP.
2. Replaces `mz_score()` occurrences with a reference to a score column
   appended after `t`'s columns, and builds the remaining `SafeMfpPlan` over
   `(row ++ score)`.
3. Emits a new `FastPathPlan::PeekBm25 { coll_id, idx_id, query, mfp }`.

The rewrite finds its index in the catalog and builds the fast path plan
directly, without consulting the dataflow's `index_imports`. Nothing is lost by
that. Read holds and timestamp selection come from `sufficient_collections`,
which names the BM25 index. EXPLAIN's "Used Indexes" comes from
`FastPathPlan::used_indexes`, which reads `idx_id` off the plan variant and
reports a full scan.

The plan lowers to a new `PeekTarget::Bm25Index { id, query }` variant, which
carries the search query to the replica. `PeekTarget` is plain serde, no proto
changes needed. `ORDER BY` and `LIMIT` ride the existing `RowSetFinishing`
untouched, since `mz_score()` is a plain output column by that point.

### Compute: rendering and storage

* `export_index` builds the BM25 arrangement in addition to the standard RowRow
  one, not instead of it. The BM25 arrangement keys the raw collection by the
  text column extracted as a `String`, dropping NULLs, with the full `Row` as
  the value, and arranges with the ported `Bm25Batcher`, `Bm25Builder`, and
  `Bm25Spine`. Each batch the builder seals builds its inverted index.
* Keeping the standard arrangement costs a second copy of the data in memory.
  That buys leaving frontier reporting, the output probe, dataflow error
  logging, and the errs trace exactly as they are for every index, BM25 or not.
  The BM25 peek reads its rows from `bm25_traces` and its errors from the
  standard bundle.
* `TraceManager` gains a parallel map, `bm25_traces: BTreeMap<GlobalId,
  Bm25Agent>`, holding the BM25 oks trace alone. A BM25 index has an entry in
  both maps. `allow_compaction`, `maintenance`, and `remove` reach into both,
  so the controller's bookkeeping is unchanged.
* The BM25 arrangement is a separate operator chain behind its own exchange,
  with no probe tying it to the standard arrangement's pace, so its upper can
  trail the standard bundle's. A peek must therefore judge readiness on the
  BM25 trace's own upper. The standard bundle's frontier can lead it and says
  nothing about whether the BM25 trace is settled.

### Compute: peek execution

A new branch in peek handling (src/compute/src/compute_state.rs) matches
`PeekTarget::Bm25Index`, looks up the trace in `bm25_traces`, and:

1. Visits each batch via `map_batches`.
2. Runs the bag-of-words query against the batch's embedded `Bm25Index`,
   producing doc id to score. A batch whose index is not built, which is any
   batch produced by a merge, gets one rebuilt from its texts first.
3. Maps doc ids back to `(key, row, time, diff)` through the batch cursor.
4. Accumulates per `(key, row)`: diffs summed for times less than or equal to
   the peek timestamp, score taken from the newest batch in which the pair has
   a nonzero net change.
5. Emits `(row ++ score)` for entries with positive accumulated count, then
   applies the `SafeMfpPlan` and hands rows to the existing finishing and
   response path.

Each worker answers over its own shard, as with regular index peeks.

## Known POC approximations

Documented, deliberately not fixed:

* IDF statistics are per batch and per worker. Scores are only globally
  consistent once compaction has merged history into a single batch per
  worker. Rows present in a batch as retractions still count toward that
  batch's corpus statistics.
* Any `@@@` query the rewrite does not match (joins, a non-literal query
  string, no BM25 index on the filtered column) is a planning error.
* No fuzzy matching, no boolean query syntax, no configurable tokenizer or
  BM25 parameters.
* The search arrangement answers peeks only. No dataflow imports it, so an
  `@@@` call outside a peek has nothing to run against. The standard
  arrangement the same index carries is under no such restriction and feeds
  dataflows like any other index's.
* The clean planning error covers peeks only, because the check lives in
  `create_fast_path_plan`. `@@@` inside a materialized view, a `SUBSCRIBE`, or
  a `COPY TO` still builds a dataflow and reaches `bm25_match`'s `eval`, which
  returns `EvalError::Unsupported`. The DDL succeeds and every row that reaches
  the operator errors, so the collection is all errors. Closing this needs a
  check on the general planning path, not just the peek one.
* A BM25 index and a plain index cannot share a key on one cluster, in either
  order of creation, and a BM25 index cannot be created on a recursive view.
  All three are rejected before the catalog commits, the shared key in
  `plan_create_index` and the recursive target in the index optimizer, which is
  the first place that shape is visible. Neither shape can be rendered:
  reusing a plain index's arrangement hands back a standard `TraceBundle` with
  no search trace beside it, and index export in an iterative scope has no BM25
  counterpart at all. Rendering keeps a check for each as defense in depth, an
  `expect` on the search trace lookup in the arrangement reuse path and an
  assert at the head of iterative index export. Two indexes of the same kind
  never conflict. A second BM25 index on the same key and cluster reuses the
  first's arrangement and registers both of its traces under the new index id,
  the way duplicate plain indexes share one arrangement.
* The shared-key rule applies to interactive planning only. Catalog rehydration
  re-plans every committed item, in an order that can present a sibling index as
  already existing, so a rule enforced there would turn a state the catalog
  already holds into a boot failure. `plan_create_index` tells the two apart by
  the presence of a plan context, which `CatalogState::deserialize_item` does
  not supply.
* An index's reported frontier follows its standard arrangement, which the
  search arrangement can trail. A search peek at a timestamp the standard
  arrangement already serves therefore blocks on the replica until the search
  trace catches up. That is a freshness cost on searches, not a correctness
  one, since the peek judges readiness on the search trace's own upper.
* The BM25 arrangement's stream is not passed through `expire_stream_at`, so it
  does not honor dataflow expiration. It also gets no arrangement size logging,
  because `MzArrange` cannot host `Bm25Spine`.

## Testing

* Unit tests in `mz-bm25` cover the tokenizer, the index, scoring, and the
  container's seal and merge behavior. Unit tests in `coord::peek` cover the
  rewrite, including the shapes it declines.
* `test/testdrive/bm25.td` is the end-to-end smoke test: create table, insert
  documents, create the BM25 index, run `@@@` queries with `mz_score()`
  ordering, check `EXPLAIN` routes through the fast path, and check that
  updates and deletes are reflected. No absolute score is asserted, since a
  document's score depends on which documents share its worker. The one ranking
  assertion runs on a single-worker cluster so that every document shares one
  corpus. A second table loaded by twenty single-row inserts covers the
  merged-batch path, where the peek rebuilds an inverted index the merge did not
  carry over. The rejected shapes have their own cases: flag off, a key already
  indexed on the same cluster in both orders, and a recursive target. The same
  pair on separate clusters is asserted to succeed. Rehydration is not covered,
  which would need a platform check.
* `cargo check` and `bin/fmt` stay green. No further CI wiring.
