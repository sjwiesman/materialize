# BM25 full text search stage two: query language and misspellings (POC)

## Summary

Stage two extends the BM25 POC (`doc/developer/design/20260731_bm25_fts_poc.md`)
with a Lucene-style query language on the right-hand side of `@@@`: boolean
operators with parentheses, quoted phrase queries, explicit fuzzy matching for
misspellings, and prefix matching. The goal is a search surface expressive
enough for AI agents, which emit Lucene-style syntax reliably from training
exposure to Elasticsearch and Lucene.

```sql
WHERE body @@@ 'databse~1 AND (streaming OR "real time")'
WHERE body @@@ 'materialized NOT view'
WHERE title @@@ 'incremen*'
```

Stage two stacks on the `bm25-fts-poc` branch at the same POC bar: peeks only,
flag-gated, panics acceptable outside the happy path, and every stage one
query keeps its exact semantics.

## Query language

Grammar, precedence low to high (OR and adjacency at the same level, then
AND, then NOT):

```
query    := or_expr
or_expr  := and_expr ((OR | adjacency) and_expr)*
and_expr := unary (AND unary)*
unary    := NOT unary | primary
primary  := '(' query ')'
          | '"' words '"'
          | term '~' N
          | term '*'
          | term
```

* Bare adjacency means OR, so `'running shoes'` keeps its stage one
  bag-of-words meaning. Backward compatibility with every existing query is a
  hard requirement.
* `AND`, `OR`, `NOT` are recognized only as uppercase keywords. Lowercase
  `and`, `or`, `not` are search terms, matching Lucene.
* Semantics map onto must/should/must_not clauses. `AND` groups are
  conjunctive (a document must match every conjunct). `OR` and adjacency are
  disjunctive. `NOT` excludes matching documents. Scores are the sum of the
  document's scores across matching positive clauses. The port template is
  upstream dd-bm25's `Query::Bool` and `evaluate_bool`.
* A query with no positive clause, for example `'NOT foo'`, is rejected at
  planning.
* `~N` accepts N in 0..=2. `~0` forces exact match. Larger N is a parse
  error.
* Operator parsing happens before tokenization, so `databse~1` applies the
  edit distance to the token `databse`, and a quoted phrase is tokenized
  into its member terms after the quotes are recognized.
* An empty query, or a query all of whose terms tokenize to nothing, matches
  no documents (stage one behavior, unchanged).

## Architecture

The parser and the richer evaluation live in `mz-bm25`. The query string
remains the wire format: `PeekTarget::Bm25Index { id, query }` is unchanged,
and the replica parses at peek time. The adapter's rewrite calls the same
parse function once at plan time purely for validation, so syntax errors and
pure-negative queries surface as clean planning errors instead of reaching a
replica. Parsing twice costs microseconds per peek. No protocol, dispatch, or
render changes.

### Parser (mz-bm25, new module `parse`)

A hand-rolled recursive-descent parser producing:

```rust
pub enum Query {
    Term { term: String, edit_distance: u32 },
    Prefix { prefix: String },
    Phrase { terms: Vec<String> },
    Bool { must: Vec<Query>, should: Vec<Query>, must_not: Vec<Query> },
}

pub fn parse_query(input: &str) -> Result<Query, QueryParseError>
```

`QueryParseError` carries a human-readable message with the offending
position. No new dependencies.

### Index changes (mz-bm25)

* `Posting` gains `positions: Vec<u32>`, the token offsets of the term within
  the document, populated by `Bm25Index::build`. Seal-time builds and the
  lazy rebuild for merged batches share that one function, so merged batches
  inherit positions with no extra work.
* The term dictionary stays the sorted `BTreeMap`. Two new lookups beside
  `get_postings`:
  * `terms_with_prefix(&str)`: a range scan over the map.
  * `terms_within_distance(&str, u32)`: a banded Levenshtein scan over the
    dictionary with per-row early exit. For batch-sized dictionaries this is
    fast enough, and it avoids re-adding the `fst` dependency and its
    licensing plumbing. If profiling ever shows this hot, an FST is the
    known upgrade path.
* Fuzzy and prefix expansion is capped at 64 terms, selected rarest first by
  document frequency. Hitting the cap truncates silently. The cap keeps a
  one-letter prefix from expanding to the whole dictionary.

### Evaluation (mz-bm25)

`evaluate` takes `&Query` instead of a raw string:

* `Term` with edit distance 0 scores as stage one.
* `Term` with edit distance N expands via `terms_within_distance` and scores
  as an OR of the expansions. No edit-distance decay on scores.
* `Prefix` expands via `terms_with_prefix` and scores as an OR of the
  expansions.
* `Phrase` intersects the member terms' postings by document, verifies
  consecutive positions (each next term at position previous + 1), and
  scores matching documents as the sum of the member terms' BM25 scores.
* `Bool` evaluates must/should/must_not per upstream semantics: must clauses
  all required, should clauses add score (and at least one is required when
  there are no must clauses), must_not excludes.

Everything stays per batch. The compute peek loop, accumulation map, score
selection, and readiness rules from stage one are untouched.

### Plan-time validation (adapter)

`bm25_fast_path` calls `mz_bm25::parse_query` on the extracted literal. A
parse error becomes a planning error in the same family as stage one's other
rejections (SQLSTATE 0A000, message "invalid search query: <detail>").
`mz-adapter` gains a dependency on `mz-bm25`.

## Testing

* Parser unit tests: precedence, parentheses, keywords vs lowercase terms,
  phrases, `~N` bounds, `*`, error positions, pure-negative rejection.
* Index unit tests: positions correctness, prefix and fuzzy lookups, the
  expansion cap, merged-batch rebuild carrying positions.
* Evaluation unit tests: each node type plus nesting, phrase adjacency
  versus mere co-occurrence, must_not exclusion.
* `test/testdrive/bm25.td` extensions: boolean queries, a phrase that
  distinguishes adjacent from non-adjacent terms, a misspelling matched via
  `~1`, a prefix query, plan-time rejection of a syntax error and of a
  pure-negative query, and ranking assertions on the single-worker cluster.

## Known POC approximations

Documented, deliberately not fixed:

* Fuzzy scoring has no edit-distance decay, so a distance-2 expansion scores
  the same as an exact match of that expansion.
* Expansion caps truncate silently at 64 terms.
* Phrase scores are member-term sums over phrase-matching documents, not a
  phrase-frequency BM25.
* Per-batch and per-worker IDF caveats from stage one apply unchanged.
* The ASCII tokenizer bounds both documents and queries, so non-ASCII text
  remains unsearchable and `~N` cannot bridge it.
