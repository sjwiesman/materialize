# mz-deploy mdbook Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship a Rust-book-style mdbook teaching new users `mz-deploy`, co-located at `src/mz-deploy/book/`, with twelve narrative chapters covering the lifecycle (write → apply → compile → test → stage → promote) and the three concept chapters (stable API, profiles, variables), plus an auto-generated command reference appendix mirrored from `src/mz-deploy/src/cli/help/*.md`.

**Architecture:** Vanilla `mdbook` (no preprocessors). Narrative chapters are hand-written under `book/src/`. The command reference appendix is generated by a POSIX shell script (`book/generate-reference.sh`) that copies the existing CLI help files into `book/src/reference/` (gitignored) and rewrites a marker-delimited block in `SUMMARY.md`. A CI lint step regenerates SUMMARY's reference block and fails on drift. An example "first-project" SQL tree lives under `book/examples/first-project/` for the walkthrough chapter.

**Tech Stack:** `mdbook` (Rust crate, installed via `cargo install mdbook` or system package), POSIX `sh`, existing repo CI shell-script conventions (`ci/test/*.sh`).

**Spec:** `docs/superpowers/specs/2026-05-28-mz-deploy-mdbook-design.md`

## Conventions used in every chapter task

Each chapter is delivered as one task. Every chapter file MUST:

- Open with a single-sentence **"What you'll learn"** line in italics.
- Close with a **"You can now…"** bullet list (2–4 bullets) summarizing concrete reader capabilities.
- Use H2 (`##`) for major sections, H3 (`###`) for subsections — no H1 except the chapter title.
- Use fenced code blocks with the appropriate language tag (`sql`, `toml`, `bash`, `text`).
- Use mdbook relative links: `[stage chapter](./ch08-staging.md)`, `[Appendix A](./appendix-a-reference.md)`.
- Never use `...` or `// TODO` placeholders inside code blocks.
- Use the support-ticket-SLA domain for examples (per spec: not "analytics").

Every chapter task ends with the same verification + commit pattern:

1. Run `mdbook build src/mz-deploy/book` — expect zero warnings, zero errors.
2. Run `mdbook serve src/mz-deploy/book` briefly, confirm the new chapter renders.
3. `git add` the chapter file plus any updates to `SUMMARY.md`.
4. Commit with message `mz-deploy book: <chapter title>`.

- [ ] **Step 3: Write the generator script**

`src/mz-deploy/book/generate-reference.sh`:

```bash
#!/usr/bin/env bash
# Regenerates the book's command reference appendix.
#
# Copies every *.md file from $HELP_DIR (default: ../src/cli/help) into
# $BOOK_SRC/reference/, then rewrites the marker-delimited block in
# $BOOK_SRC/SUMMARY.md to list one entry per file, alphabetically sorted.
#
# Markers in SUMMARY.md must look like:
#   <!-- BEGIN REFERENCE -->
#   <!-- END REFERENCE -->

set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
HELP_DIR="${HELP_DIR:-$SCRIPT_DIR/../src/cli/help}"
BOOK_SRC="${BOOK_SRC:-$SCRIPT_DIR/src}"

REF_DIR="$BOOK_SRC/reference"
SUMMARY="$BOOK_SRC/SUMMARY.md"

if [ ! -d "$HELP_DIR" ]; then
    echo "error: HELP_DIR does not exist: $HELP_DIR" >&2
    exit 1
fi
if [ ! -f "$SUMMARY" ]; then
    echo "error: SUMMARY.md not found: $SUMMARY" >&2
    exit 1
fi

# 1. Mirror help/*.md into book/src/reference/.
rm -rf "$REF_DIR"
mkdir -p "$REF_DIR"
for f in "$HELP_DIR"/*.md; do
    cp "$f" "$REF_DIR/"
done

# 2. Build the new SUMMARY block.
BLOCK="$(mktemp)"
trap 'rm -f "$BLOCK"' EXIT
{
    echo '<!-- BEGIN REFERENCE -->'
    for f in "$REF_DIR"/*.md; do
        name="$(basename "$f" .md)"
        printf -- '- [%s](./reference/%s.md)\n' "$name" "$name"
    done | LC_ALL=C sort
    echo '<!-- END REFERENCE -->'
} > "$BLOCK"

# 3. Splice the new block into SUMMARY.md between the markers.
awk -v block_file="$BLOCK" '
    BEGIN { in_block = 0; printed = 0 }
    /<!-- BEGIN REFERENCE -->/ {
        if (!printed) {
            while ((getline line < block_file) > 0) print line
            close(block_file)
            printed = 1
        }
        in_block = 1
        next
    }
    /<!-- END REFERENCE -->/ {
        in_block = 0
        next
    }
    !in_block { print }
' "$SUMMARY" > "$SUMMARY.tmp"

mv "$SUMMARY.tmp" "$SUMMARY"
```

IN CLUSTER app
AS
SELECT
    id,
    opened_at,
    sla_minutes,
    closed_at,
    CASE
        WHEN closed_at IS NULL
             AND mz_now() > opened_at + (sla_minutes * INTERVAL '1 minute')
        THEN 'breached'
        WHEN closed_at IS NOT NULL
             AND closed_at > opened_at + (sla_minutes * INTERVAL '1 minute')
        THEN 'closed_breached'
        ELSE 'on_time'
    END AS status
FROM tickets;

5. **When to reach for stable** — published contracts; cross-team boundaries; MV surfaces that other `mz-deploy` projects subscribe to.
6. **When *not* to use it** — anything mid-iteration; anything with table/view/sink/source mixed in.
7. **Worked example** — a schema mod file containing `SET api = stable;` and one MV file under that schema directory.

## Task 18: Appendix B — Glossary

- [ ] **Step 1: Fill in the glossary**

Replace the placeholder with definitions for every term the book introduces. Each entry is one or two sentences. Terms (alphabetical):

- **apply** — the `mz-deploy` command that converges Materialize infrastructure (clusters, roles, network policies, secrets, connections, sources, tables) toward what your project declares.
- **deploy ID** — the suffix used on staging schemas and clusters during `stage`. Defaults to the first seven characters of the current git commit SHA.
- **deferred sink** — a sink defined in a staging deployment whose creation is held back until `promote`, so it does not start producing rows from staging data.
- **dirty (object)** — an object whose definition has changed since the last promoted snapshot, or whose dependencies have changed. Dirty objects are redeployed by `stage`.
- **profile** — a named set of connection details for a Materialize instance, defined in `profiles.toml`.
- **profile variant file** — a `name__<profile>.sql` file that overrides `name.sql` when the active profile matches.
- **project** — a directory tree containing `project.toml` and SQL files that declares the desired state of a Materialize installation.
- **promote** — the `mz-deploy` command that atomically swaps a staged deployment into production.
- **replacement MV** — a materialized view in a `SET api = stable` schema whose changes are applied in place via `ALTER MATERIALIZED VIEW ... APPLY REPLACEMENT` rather than schema swap.
- **schema modifier file** — a `models/<database>/<schema>.sql` file containing directives (e.g. `SET api = stable;`) that apply to the entire schema.
- **stable API schema** — a schema marked with `SET api = stable`, restricted to materialized views only, whose objects can be safely depended on by other teams or other `mz-deploy` projects.
- **stage** — the `mz-deploy` command that builds a staging deployment containing only objects that have changed since the last promoted snapshot.
- **types.lock** — a project file that pins external type information used by `compile` for type-checking without contacting a live Materialize.
- **variable** — a psql-style `:name` substitution defined per-profile in `project.toml`, resolved before the SQL parser sees the file.
