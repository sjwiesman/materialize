# mz-deploy mdbook: User Documentation Design

**Status:** Approved (design phase) — 2026-05-28
**Author:** Seth (seth@materialize.com)
**Scope:** Initial user-facing documentation for the `mz-deploy` CLI, delivered as an mdbook.

## Goal

Teach new users how to use `mz-deploy` and build a durable mental model of the tool. The book should explain *interesting* mechanics (partial staging, `SET api = stable`, unit tests) without describing implementation details. Inspiration: the Rust book's pedagogical structure, the Timely / Differential Dataflow books' terser pace and concept-first style.

## Non-goals

- Internal architecture or implementation-detail docs (those live in `doc/developer/`).
- API/library docs for the `mz-deploy` crate itself.
- A marketing site or hosted-docs publishing pipeline. The book ships as source; rendering/hosting is out of scope for v1.
- Translations, search, or analytics customizations beyond mdbook defaults.

## Audience

New users adopting `mz-deploy`. They have working SQL knowledge and have used Materialize at least casually, but have not used `mz-deploy` before. They are evaluating the tool or about to ship their first project with it.

## Mental model the book teaches

Lifecycle first: **write → compile → stage → promote**. Each phase is a chapter; each chapter names one mechanism and explains why it exists. Concepts that change project design (stable API, profiles, testing) come after the lifecycle is grounded.

## Location and build

- **Path:** `src/mz-deploy/book/` — co-located with the crate so the book is part of the `mz-deploy` deliverable.
- **Build tool:** `mdbook` (vanilla, no preprocessors in v1).
- **Preview:** `mdbook serve src/mz-deploy/book`.
- **Layout:**
  - `src/mz-deploy/book/book.toml`
  - `src/mz-deploy/book/src/SUMMARY.md` (hand-written; includes generated reference entries)
  - `src/mz-deploy/book/src/*.md` (narrative chapters)
  - `src/mz-deploy/book/src/reference/*.md` (generated; gitignored, regenerated by script)

## Structure

### Part I — Introduction

1. **What is mz-deploy?** — the pitch in one chapter. What problem it solves; what a project is; one-paragraph teaser of the lifecycle.
2. **Installation & setup** — `mz-deploy setup`, creating the first profile, sanity-checking the connection.
3. **Your first project** — guided walkthrough: `new` → write a tiny project (one source-less view or pre-existing table-backed view) → `compile` → `stage --dry-run` → `stage` → `promote`. Ends with a working deployed view.

### Part II — The Lifecycle

4. **Writing** — project layout, files-as-schemas, directory-to-namespace mapping, schema modifier files (introduces the *idea* of `SET api = stable` without diving in yet).
5. **Compiling** — what `compile` validates, the kinds of errors it surfaces, how hints work.
6. **Staging** — partial deployments: only changed objects ship. Suffixed schemas/clusters. Deploy IDs. Deferred sinks. Rollback behavior.
7. **Promoting** — atomic schema swap, replacement-MV application order, and a clearly-marked subsection on **concurrent deploys and promote conflicts** (first-promote-wins, re-stage flow).

### Part III — Concepts that change how you think

8. **Stable API schemas (`SET api = stable`)** — the most non-obvious idea in the tool. Why replacement instead of swap. What it costs (MV-only schemas). When to reach for it.
9. **Profiles & environments** — connection profiles, `__staging` / `__dev` file overrides, secret resolvers (env, file, AWS Secrets Manager, GCP Secret Manager).
10. **Testing SQL** — `mz-deploy test`, how assertions are written, what test isolation looks like.

### Part IV — Reference

- **Appendix A — Command reference.** Auto-generated from `src/mz-deploy/src/cli/help/*.md`. One page per command.
- **Appendix B — Glossary.** Short definitions of terms used throughout the book (project, profile, deploy ID, stable API, replacement MV, deferred sink, etc.).

`dev` and inspection commands (`list`, `describe`, `explain`, `log`) appear in Appendix A only — they're not given chapters in v1.

## Auto-generated reference

The reference appendix mirrors the per-command help files that ship with the CLI today (`src/mz-deploy/src/cli/help/*.md`). A small script regenerates the mirror and the reference section of `SUMMARY.md`:

- **Script:** `src/mz-deploy/book/generate-reference.sh` (POSIX sh).
- **Inputs:** all `*.md` files in `src/mz-deploy/src/cli/help/`.
- **Outputs:**
  - `src/mz-deploy/book/src/reference/<command>.md` (copied verbatim; gitignored).
  - A regenerated reference block inside `src/mz-deploy/book/src/SUMMARY.md`, delimited by `<!-- BEGIN REFERENCE -->` / `<!-- END REFERENCE -->` markers so the script can edit between them without touching hand-written entries.
- **Invocation:** run by the developer before `mdbook build`. Documented in the book's contributor section.
- **Drift check (CI):** a CI step runs the script and `git diff --exit-code` against the SUMMARY markers. Reference `*.md` files are gitignored so they never drift in tree — they're regenerated on every build. The CI check only guards the SUMMARY entries.

## Style

- Each chapter opens with a 1–2 sentence "what you'll learn" and ends with a "you can now…" recap.
- Code blocks are real and runnable: real shell commands, real SQL. No `...` placeholders.
- Cross-references use mdbook's relative-path links (`[text](./chapter.md)`).
- Terminal output blocks rather than screenshots in v1.
- Voice: direct, second-person, concrete. Match the existing `src/cli/help/*.md` register.

## Content sourcing

- Lifecycle chapters draw on the existing `src/cli/help/{compile,stage,promote,apply,test}.md` files for accuracy but rewrite them in narrative form. The help files are the source of truth for behavior; the book is the source of truth for *teaching*.
- The "Your first project" walkthrough uses a fresh example project authored for the book — kept under `src/mz-deploy/book/examples/first-project/` so it can be sanity-tested against a real cluster.
- Example domain: NOT analytics (positioning conflict per project standards). Use an operational/event-driven example — e.g., support-ticket SLA tracking, IoT device status, or similar.

## Out of scope for v1 (explicitly deferred)

- Per-chapter exercises or "try this" boxes.
- Diagrams (mermaid or otherwise). Plain prose for v1.
- Tutorial chapters for `dev` and inspection commands.
- Linkchecking via `mdbook-linkcheck`.
- Hosted publishing. The book is buildable locally; where/how it's served lives outside this spec.

## Success criteria

- A new user can read Part I and ship a real `stage` → `promote` in under an hour.
- After Part II, a user can predict what `stage` will do without running `--dry-run`.
- After Chapter 8, a user can explain in their own words when `SET api = stable` is worth the constraints.
- Appendix A is byte-identical to `src/cli/help/*.md` after running the generator. CI enforces SUMMARY consistency.

## Open questions

None at design time. Implementation plan will own decisions like exact filenames, anchor IDs, and example project shape.
